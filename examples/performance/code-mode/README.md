# Живое Сравнение CodeMode

Стенд сравнивает прямые tool calls и `code_mode` на одной подключённой модели.
Он запускает готовый release CLI, ничего не собирает и сохраняет новую сессию
для каждого случая. Используется действующая авторизация модели; запуск
расходует её квоту. Задания и данные синтетические, сервис работает локально
через stdio MCP.

```sh
python3 examples/performance/code-mode/run.py \
  --output target/performance/code-mode/my-live-run
```

По умолчанию: модель `gpt-5.6-luna`, reasoning `high`, runtime из соседнего
`Proteus-desktop/build/Proteus`, профиль `configs/code-mode.config.toml`.
Другой готовый executable и профиль выбираются через `--binary` и
`--base-config`; модель — через `--model` и `--reasoning`. Профиль должен
содержать настроенный `chatgpt` provider. Существующее окружение portable
подхватывается без печати его значений. `--output` должен быть новым каталогом.

## Задачи И Проверка

| Сценарий | Требование | Независимая проверка |
|---|---|---|
| `audit` | Пройти страницы 64 карточек, прочитать каждую, отобрать совпадения и посчитать итоги | Точный JSON отчёта, все 64 карточки прочитаны, состояние не изменилось |
| `update` | Из 48 карточек перенести ровно 16 в Backlog и проверить каждую запись | Точный отчёт, diff всего состояния только по разрешённому полю/карточкам, get до и после каждого update |

Страницы содержат только opaque IDs, cursor нужно получать из предыдущего
ответа. Описание карточки включает обычный длинный текст, который не нужен
в итоговом отчёте. Сервис не добавляет искусственные задержки и не сообщает
модели правильный ответ. Данные и API log находятся вне рабочего каталога
агента. Повторные updates и лишние отправки отчёта не маскируются scorer-ом.

Оба режима получают одни MCP tools и одинаковые исходные данные. Прямые
вызовы могут объединяться в одном ответе модели. В CodeMode включён только
дополнительный инструмент и инструкция использовать его для orchestration;
скрипт пишет сама модель. Shell и file tools не доступны обоим режимам:
это исследование API orchestration, не сравнение решения произвольных
coding-задач. Прямые определения API tools остаются видимыми и в CodeMode.

Первый сценарий выполняется в порядке direct → code-mode, второй — наоборот.
По умолчанию делается один прогон каждого режима на задачу. `--case` и
`--mode` позволяют явно выбрать подмножество. Одинаковый watchdog задаётся
через `--timeout`; network/model failures и неуспешные попытки сохраняются.
Сборки и другие замеры одновременно со стендом не запускайте.

Для отдельной проверки качества контракта API передайте `--api-schemas`:
сервер объявит `outputSchema` и точные поля/типы входного отчёта. Они не
содержат правильных IDs, количества совпадений или итоговых сумм. Без флага
сохраняется исходная форма API без этих схем; это позволяет проверять правку
описания CodeMode отдельно от улучшения API. Не объединяйте результаты этих
условий в одну оценку эффекта инструкции.

## Метрики И Артефакты

`report.json` и `report.md` содержат время всего CLI, model requests, provider
input/output/cache/reasoning tokens, root и nested tools, число реальных API
calls и проверку результата. Cached input входит во входные токены, reasoning
входит в выходные. Если provider usage покрывает не все запросы, total
показывается как `n/a`; частичные суммы и покрытие остаются в JSON. Долларовая
стоимость не вычисляется.

Счётчик API calls берётся из независимого сервисного журнала; один `code_mode`
не считается одним реальным API call. Canonical tool-result bytes — размер
JSON с metadata, а не provider wire bytes и не токены. В режиме CodeMode
проверяйте наличие настоящих nested MCP calls и отдельно отмечайте hybrid,
если модель вызвала часть API напрямую.

Каждый прогон сохраняет config, prompt, stdout/stderr, fixture, ожидаемое и
фактическое состояние, API audit log и canonical journal. Reader проверяет
последовательность журнала и hashes внешних blobs. В сводке фиксируются
ревизии, SHA256 бинарника и исходников стенда, одинаковость fixtures между
режимами. Эти артефакты остаются под `target/performance/`.

Модель и reasoning проверяются по каждому canonical request; hashes реальных
ToolSpec позволяют отличить новое описание от старого установленного модуля.
Scorer также требует отправить единственный отчёт после всех остальных
API-операций: угаданный правильный отчёт до работы не считается выполнением.

Сравнивайте экономию и время между успешно решёнными случаями. Один прогон
на режим — наблюдение по конкретным задачам; cache, нагрузка сервера и
вариативность модели не дают по нему устойчивой оценки всего агента.
