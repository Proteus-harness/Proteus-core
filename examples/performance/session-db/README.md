# Локальное чтение сессий: SQLite и Turso

Самостоятельный воспроизводимый эксперимент для выбора движка read index.
Он не меняет хранилище Proteus. Версии всех зависимостей закреплены в Cargo.lock;
сравниваются native SQLite через rusqlite 0.41.0 и Turso 0.8.0 без sync/FTS.

```sh
cd examples/performance/session-db
CARGO_BUILD_JOBS=2 cargo build --release --locked
python3 run.py
```

Данные создаются под `target/measure-*` на файловой системе checkout:
512 сессий, 102400 одинаковых Unicode JSON-сообщений. Оба движка используют
одинаковые таблицы, индексы, WAL и synchronous=FULL. Чтение открывает новый
процесс, выбирает список с LIMIT 50 и последние 50 сообщений, затем проходит
историю страницами по ключу. Запись — 100 отдельных autocommit событий.
Семь прогонов чередуют порядок движков; результаты запросов обязаны совпадать.
`report.json` содержит все измерения и медианы, время не является assertion.

Это single-writer измерение на прогретом файловом кэше ОС. Оно не сравнивает
MVCC/concurrent writers, не очищает системный кэш, не измеряет реальный turn,
GPU или полный запуск приложения. Стоимость процесса выводится отдельно;
`open_ms` включает открытие движка и применение одинаковых PRAGMA.

На локальном прогоне 26.10.2026 медианы в миллисекундах:

| Операция | SQLite | Turso |
|---|---:|---:|
| Открыть базу и задать PRAGMA | 0.515 | 2.293 |
| Первый список 50 сессий | 0.046 | 0.233 |
| Первая страница 50 сообщений | 0.250 | 0.291 |
| Прогретая страница, включая проверку результата | 0.139 | 0.076 |
| 100 отдельных durable записей | 92.836 | 97.537 |

Один движок не выигрывает во всех операциях. В этом сценарии SQLite дешевле
при открытии и первом чтении, Turso быстрее на повторных страницах. Эти цифры
не доказывают ускорение Proteus от миграции: это требует отдельной проверки
инвалидации проекций, объёма декодирования и фактического первого кадра.
