# Локальное чтение сессий: SQLite и Turso

Самостоятельный воспроизводимый эксперимент для выбора движка read index.
Он не меняет хранилище Proteus. Версии всех зависимостей закреплены в Cargo.lock;
сравниваются native SQLite через rusqlite 0.41.0 и Turso 0.8.0 без sync/FTS.

```sh
cd examples/performance/session-db
CARGO_BUILD_JOBS=2 cargo build --release --locked
python3 run.py
```

Данные создаются под `target/measure-*` на файловой системе checkout:
512 сессий, 102400 одинаковых Unicode JSON-сообщений. Оба движка используют
одинаковые таблицы, индексы, WAL и synchronous=FULL. Чтение открывает новый
процесс, выбирает список с LIMIT 50 и последние 50 сообщений, затем проходит
историю страницами по ключу. Запись — 100 отдельных autocommit событий.
Семь прогонов чередуют порядок движков; результаты запросов обязаны совпадать.
`report.json` содержит все измерения и медианы, время не является assertion.

Это single-writer измерение на прогретом файловом кэше ОС. Оно не сравнивает
MVCC/concurrent writers, не очищает системный кэш, не измеряет реальный turn,
GPU или полный запуск приложения. Стоимость процесса выводится отдельно;
`open_ms` включает открытие движка и применение одинаковых PRAGMA.

На локальном прогоне 26.10.2026 медианы в миллисекундах:

| Операция | SQLite | Turso |
|---|---:|---:|
| Открыть базу и задать PRAGMA | 0.515 | 2.293 |
| Первый список 50 сессий | 0.046 | 0.233 |
| Первая страница 50 сообщений | 0.250 | 0.291 |
| Прогретая страница, включая проверку результата | 0.139 | 0.076 |
| 100 отдельных durable записей | 92.836 | 97.537 |

Один движок не выигрывает во всех операциях. В этом сценарии SQLite дешевле
при открытии и первом чтении, Turso быстрее на повторных страницах. Эти цифры
не доказывают ускорение Proteus от миграции: это требует отдельной проверки
инвалидации проекций, объёма декодирования и фактического первого кадра.

## Измеримый прототип расхода памяти

```sh
cd examples/performance/session-db
CARGO_BUILD_JOBS=1 cargo build --release --locked --bin session-memory
python3 memory.py
# Границы страницы и неполная последняя страница:
python3 memory.py --rows 50 51 --repeats 1
```

`session-memory` — отдельный Rust executable. Он создаёт синтетическую историю
в `target/memory-*`: Unicode-тексты и результаты tools с полями формы
`AppTranscriptMessage`, без настоящих сессий. Один JSONL используется для
наполнения обеих баз; payload в них побайтно одинаков. SQLite и Turso используют
WAL, synchronous=FULL и явно заданный page cache 2 МиБ.

Сравниваются шесть режимов, каждый в новом процессе:

- JSONL, SQLite и Turso с удержанием всей декодированной истории;
- JSONL с последовательным сканированием и удержанием последних 50 сообщений;
- SQLite и Turso с индексной выборкой последних 50 сообщений и последующим
  обходом истории страницами по ключу, без накопления предыдущих страниц.

Проверяются длина, непрерывность и порядок SQL-страниц, идентичность последних
50 сообщений и digest всей истории. В обоих SQL-режимах статистика читает
`count(*)`; в таблице нет отдельного готового счётчика. Поэтому даже время
первой SQL-страницы здесь не обязано оставаться постоянным с ростом истории.
JSONL с ограниченным окном тоже сохраняет RAM, но для получения хвоста
сканирует всю историю. Это разделяет эффект движка и способа чтения данных.

`report.json` содержит все повторы и медианы. Память снимается через Linux
`/proc/self/smaps_rollup` перед открытием, после открытия, после первой
полезной страницы, после полного обхода и после освобождения сообщений.
Основной показатель — **PSS + SwapPss**: вытеснение в swap не считается
экономией. Также сохраняются RSS, private pages и приблизительный Linux
VmHWM; последний не включает swap. CPU time, major page faults и системные
memory PSI помогают заметить влияние посторонней нагрузки. После `drop`
аллокатор может оставить освобождённые страницы у процесса.

На повторном локальном прогоне 26.10.2026, три повтора каждого режима,
медиана PSS + SwapPss после готовности последних сообщений, МиБ:

| Чтение | 1 000 сообщений | 5 000 | 20 000 |
|---|---:|---:|---:|
| JSONL, вся история | 9.07 | 33.41 | 124.97 |
| SQLite, вся история | 12.74 | 37.08 | 128.75 |
| Turso, вся история | 20.06 | 44.63 | 136.06 |
| JSONL, окно 50 | 3.24 | 3.32 | 3.21 |
| SQLite, страница 50 | 6.88 | 6.96 | 6.96 |
| Turso, страница 50 | 14.82 | 14.81 | 14.79 |

Данные на 20 000 сообщений занимали 90.0 МиБ в JSONL и 117.4 МиБ в каждой
базе. После обхода всей истории расход памяти страничных SQL-режимов остался
практически тем же. Отдельный прогон на 50 и 51 сообщении проверил полную
и неполную страницы; всего в этом измерении прошли 90 чтений.

**Результат относится к этому прототипу:** основную экономию даёт ограничение
декодированной истории; SQLite здесь требует меньше памяти, чем Turso.
Простая смена JSONL на SQL при прежней полной загрузке экономии не дала.
Предыдущий прогон попал под сильное давление памяти и дал нестабильные времена;
не переносите его задержки или даже повторные времена на полный запуск Proteus.
Время в отчёте включает проверки результата и инструментирование; кэш ОС
прогрет, посторонняя нагрузка не контролируется.

Это не замер текущего Core: здесь нет model context, нескольких проекций,
канонической валидации журнала, восстановления после сбоя, concurrent writer
или GPU. Прототип не мигрирует сессии, не подключён к runtime и не заменяет
канонический журнал. Перед интеграцией потребуются отдельные проверки
инвалидации индекса, replay/recovery и RAM настоящего процесса с тем же сценарием.
