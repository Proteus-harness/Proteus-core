# Повторная сборка после изменения исходника

Стенд использует существующий Cargo target и не запускает `cargo clean`.
Запуск явно изменяет один чистый tracked-файл проекта и восстанавливает его
исходные байты в `finally`. При обнаружении чужого изменения этого файла стенд
останавливается, сохраняя чужие байты. Не редактируйте выбранный файл параллельно.
Каталог результата должен отсутствовать: предыдущие измерения не перезаписываются.
Исходные байты дополнительно сохранены в результате как `source.original`.

```sh
python3 examples/performance/build-iteration/run.py \
  --project ../Proteus-desktop --package proteus-native \
  --profile fast --jobs 2 --repeats 3 \
  --output ../Proteus-desktop/build/verification/build-iteration-current \
  --edit-file crates/diff/src/parse.rs \
  --old 'a file was started' --new 'a diff file was started'
```

Для Desktop до выделения diff-crate укажите `--edit-file src/diff/parse.rs`.
Для измерения shipping-профиля используйте `--profile release`. Сравнивайте
одинаковые профили, toolchain, jobs, feature-набор и состояние внешних зависимостей.
Переменная `CARGO_TARGET_DIR`, если задана, сохраняется: обе стороны сравнения
должны использовать сопоставимые фиксированные каталоги. Опция `--timings`
включает Cargo HTML timings; Cargo сохраняет их в своем target/cargo-timings.

Сначала выполняется отдельная прогревающая сборка. Каждый повтор содержит:

1. `noop`: сборку без изменений после прогрева/предыдущего восстановления.
2. `edit`: замену ровно одного вхождения строки и сборку измененного содержимого.
3. `restore`: восстановление исходных байтов и отдельную сборку восстановления.

Каждый `edit` использует одну и ту же пару содержимого; простое обновление mtime
не заменяет содержательное изменение. `restore` не включается во время `edit`.
Прогрев и восстановление могут быть дорогими и представлены отдельными фазами.
Провал сборки завершает измерение, сырой stdout/stderr остаётся в результате.
При провале `edit` исходник восстанавливается, но сборка восстановления не запускается.

`report.json` содержит commit, выбранный профиль и определения профилей manifest,
версии Cargo/rustc, влияющие переменные окружения, SHA-256 исходного/измененного
файла, результаты фаз и median/minimum/maximum. В JSON каждой фазы также есть
Cargo compiler-artifacts с `fresh`, package ID и target: число artifacts не равно
числу уникальных packages. Сырые Cargo JSON и stderr сохраняются отдельно.

`wait4_maxrss_kib` — Linux `ru_maxrss` Cargo и его ожидаемых дочерних процессов.
Это не сумма RSS процессов и не одновременный пик дерева; PSS этой метрикой
не измеряется. Wall time измеряется монотонными часами; user/system — `wait4`.
Для запуска стенда в целевом проекте не должно идти других Cargo сборок: ожидание
target-lock попадёт в wall time и сделает сравнение некорректным.

Проверка самого протокола на маленьком синтетическом git-проекте, без Cargo:

```sh
python3 -m unittest discover -s examples/performance/build-iteration -p test_run.py -v
```
