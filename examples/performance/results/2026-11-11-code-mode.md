# CodeMode: Живые Прогоны 11 Ноября 2026

Продолжение с разбором причин, контрольными Sol-запусками и исправлениями —
[CodeMode follow-up](2026-11-11-code-mode-followup.md).

Текущую интеграцию CodeMode на `gpt-5.6-luna/high` рано включать по умолчанию.
Она резко сокращает обращения к модели и объём её входа, но в двух проверенных
задачах итог оставался неверным. Успешное выполнение JavaScript не доказывает
выполнение пользовательской задачи. Ускорение относительно нерешённой задачи
здесь не заявляется.

  Canonical requests подтверждают модель, temperature `0.0`, лимит входа
  200 000 и выхода 16 384 токена. Все числа токенов ниже — provider usage.
- Готовый release Core `f911694151846cbf5b7fd5b70f9cba135cb655ab` и
  Modules checkout `8329e212b662731c9c7f68f35c15b97d08050b06`.
  Core binary SHA256:
  `f47552c3183d84e6ad1ecd4bf49dad863fa7f44b5390d0d094246cc68ecb0256`.
  Обе серии использовали один бинарник. SHA256 CodeMode:
  `e71579c9042ef17fa78bb585503ef0d694b3abbb11a5c8d2504dc5bae6c1ed3d`.
- Две синтетические API-задачи через локальный stdio MCP. Прямой режим имел
  те же tools и мог объединять вызовы; реально встречались пачки до 18 calls.
  CodeMode получал дополнительный инструмент и инструкцию использовать его;
  весь JavaScript генерировала сама модель.
- Новая сессия на каждый запуск, один общий пустой cwd, данные сервиса вне cwd.
  Shell/file tools отсутствовали у обоих режимов. Это сравнение API
  orchestration, а не произвольных coding-задач и не сравнение с Factory.
- Prompt cache включён, routing key отдельный для каждой сессии.
  `stream_max_retries=0`, model timeout 120 с, workflow timeout 300 с.
  Искусственных задержек и сбоев сервиса не было; сборки одновременно не шли.

Аудит использует исходный prompt v1. Перенос — одинаково уточнённый prompt v2
из контрольного повтора, описанного ниже. PASS означает точный отчёт,
правильное полное состояние и обязательное покрытие API; завершение CLI
проверяется отдельно.

Cached input уже входит в Input; reasoning входит в Output. Вход без кэша:
51 213 / 3 134 токена для аудита Direct / CodeMode и 31 473 / 6 996 для
переноса. Денежная стоимость не вычислялась. У CodeMode при переносе реальных
API-вызовов больше, а не меньше: 94 против 87. Его root tools — три скрипта,
дочерние MCP-вызовы учтены отдельно, а не названы одним tool use.

### Аудит

Direct прошёл восемь страниц, прочитал все 64 карточки и отправил точный
отчёт: 16 совпадений, верные IDs, группы и сумма оценок.

CodeMode написал скрипт, ожидавший `p.ids` или `p.issue_ids`; сервис реально
возвращал `p.issues[].id`. Fallback `|| []` превратил ошибку контракта в пустой
набор. Скрипт прошёл страницы, не вызвал `get_issue` ни разу и отправил отчёт
об обработке нуля карточек. Затем модель запросила образец ответа, но задачу
не закончила. Поэтому малое число токенов этого случая не является доказанной
экономией при сохранении качества.

### Перенос С Уточнённым Условием

Direct выполнил ровно 16 допустимых обновлений и 16 readback, сохранил все
остальные поля/карточки и отправил точный отчёт. Canonical turn завершился
успешно.

CodeMode сначала снова угадал неправильный формат списка. На API-вызове №7
он уже отправил отчёт с `examined=0`, пустыми IDs и шестью ошибками разбора.
После отдельного запроса образца модель исправила скрипт, прочитала все 48
карточек, правильно перенесла ровно 16 и проверила каждую запись. Но ранее
отправленный отчёт остался неверным. Требование отправить единственный итог
после работы не выполнено. Состояние и readback проходят независимый scorer;
полная задача — нет.

## Исходный Pilot Переноса И Исправление Постановки

Первый prompt неоднозначно называл `examined` как «all examined issues»,
хотя oracle ожидал число 48. Массив из 48 записей тоже соответствует такой
формулировке. Этот дефект стенда исправлен на явный integer count; также
явно запрещены повторные updates. Оба режима повторены с новыми сессиями,
одинаковыми исходными данными и уточнённым условием. Исходные результаты
сохранены и не подменены успешными повторами.

| Режим, pilot v1 | Время, с | Model requests | Input | Cached input | Output | Реальные API calls | Проверка |
|---|---:|---:|---:|---:|---:|---:|---|
| CodeMode | 70,92 | 4 | 12 961 | 7 168 | 3 321 | 87 | Все 16 изменений и readback верны; тип `examined` не оцениваем из-за ambiguity |
| Direct | 201,57 | 33 | 527 598 | 493 952 | 7 548 | 92 | Две лишние карточки и одно повторное обновление |

Direct ошибочно обновил `issue_494009a773af` и `issue_fa52365043d5`:
у обеих было `approved_for_backlog=false`. Первую также обновил дважды.
Все 16 правильных тоже обработаны, итого 19 updates / 18 уникальных карточек.
Неверные IDs присутствуют в tool calls самой модели; API/transport failures
не было. Это ошибка отбора, а не самовольное изменение аргументов host.

В CodeMode pilot модель один раз передала `timeout_ms=60000` при configured
ceiling 30000. Модуль отклонил вызов до действий; модель повторила его с
допустимым бюджетом. Попытка и её токены включены в метрики.

## Отдельный Сбой CLI И Replay

В четырёх из шести запусков после записанного `TurnSettled(success)` CLI
возвратил `Error: local app-server did not stop after shutdown`. Общий deadline
request/shutdown/ожидания процесса — две секунды
([cli_app.rs](../../../crates/proteus-core/src/cli_app.rs#L118)). Проверка
shutdown происходит до печати final text
([main.rs](../../../crates/proteus-core/src/main.rs#L245)), поэтому корректно
выполненная задача выглядит как ошибка CLI. Это наблюдалось у обоих режимов;
какой teardown-путь задержал exit, этим замером не установлено.

Workflow replay контрольного CodeMode переноса совпал. SHA256 исходного
journal, API log, current state и report не изменились: повторных эффектов
не было. Replay подтверждает воспроизведение поведения, включая неверный
отчёт; это не проверка правильности пользовательской задачи.
