# CodeMode: Причины Ошибок И Контроль На Sol 6.1

В двух проверенных API-задачах идея CodeMode работает. Движок точно исполнял
переданный JavaScript; прежние неправильные результаты появились в алгоритме,
который написала модель. Наша интеграция оставляла существенные ловушки:
инструкция поощряла пакетную обработку без разведки неизвестного ответа,
MCP discovery терял объявленный `outputSchema`, а CLI мог заблокироваться
при завершении уже успешно выполненной задачи.

Это продолжение [первого сравнения](2026-11-11-code-mode.md). Его неуспешные
запуски сохранены. Неоднозначный pilot переноса исключён из причинной таблицы:
для update везде используется уточнённый prompt с integer `examined`.

## Что Разделили В Эксперименте

Сначала поменяли только конфигурацию модели: `gpt-5.6-luna/high` →
`gpt-6.1-sol/xhigh`, оставив исходный CodeMode, Core, API и данные.
Это совместная смена модели и reasoning, а не доказательство эффекта одного
reasoning level. Затем изменили только описание CodeMode и повторили оба
задания на обеих конфигурациях. Shell/file tools у всех отсутствуют;
прямым вызовам разрешены batching и parallel tool calls.

PASS ниже требует точного отчёта, полного чтения, точного diff всего состояния,
правильных readback, отсутствия повторных/лишних updates и единственного
submit после остальных API-операций. CLI exit проверяется отдельно.

| CodeMode | Модель / reasoning | Аудит 64 | Перенос 16 из 48 | Model requests, audit / update | Input tokens, audit / update |
|---|---|---|---|---:|---:|
| Исходный | Luna / high | FAIL | FAIL | 3 / 4 | 6 846 / 13 652 |
| Исходный | Sol 6.1 / xhigh | PASS | PASS | 6 / 5 | 18 113 / 16 175 |
| Новое описание | Luna / high | PASS | PASS | 4 / 5 | 10 447 / 14 763 |
| Новое описание | Sol 6.1 / xhigh | PASS | PASS | 4 / 4 | 9 793 / 11 246 |

Один запуск на каждую клетку — диагностическое наблюдение, а не оценка общей
надёжности. В instruction-only фазе нет output schemas API, typed report schema
или изменений JS runtime. Сравниваются одинаковые task prompts и fixtures.
Hashes реальных ToolSpec из canonical requests подтверждают смену описания
и неизменность четырёх MCP specs.

### Как Помогла Инструкция

Исходная Luna ожидала `ids`/`issue_ids` вместо реального `issues[].id`.
`JSON.parse` работал правильно; fallback `[]` скрывал ошибку формы. Модель
отправляла пустой отчёт до завершения работы. Исправленный вариант требует
небольшого read-only probe, проверки полей/типов/IDs/cursors, полного покрытия
выборки до записей и проверки постусловий до финализации. API не расширен:
`tools.call` по-прежнему возвращает raw `ToolResult`.

Luna при переносе всё ещё первоначально угадала неправильное поле, но теперь
guard выбросил исключение **до мутаций и отчёта**. После просмотра реального
ответа модель восстановилась. Итог: ровно 16 правильных уникальных записей,
16 точных before/after, остальные данные сохранены, правильный отчёт последним.

Восстановление было затратным: 143 API calls вместо минимальных 87.
Это 14 list + 112 get + 16 update + 1 submit. Дополнительные 56 вызовов —
только чтения: неверный probe, исправленный probe и отдельный исследовательский
проход. Модель разделила полный просмотр и рабочий проход на разные скрипты;
из-за fresh JS state вычисленные записи не переиспользовались. Это выбор
алгоритма модели: после короткого probe весь рабочий проход можно выполнить
одним скриптом, как в корректном Sol-переносе с новым описанием (87 API calls).

Исходный Sol самостоятельно делал probe и проверки формы/покрытия, поэтому
обе задачи решены ещё до исправлений. В обоих случаях он также один раз
попросил `timeout_ms=60000` при configured ceiling 30000: ошибка отклонена
до эффектов и исправлена. Новое описание явно советует оставить default и
различает общий максимум schema и настроенный ceiling; этих retries в новых
instruction-only запусках не было.

## Сопоставимые Успешные Задачи На Sol

Здесь обе стороны используют **исходный** модуль и одинаковый API без схем.
Все четыре задачи правильны. Три CLI завершились ошибкой уже после success;
это отмечено отдельно и не скрывается в оценке задачи.

уменьшились обращения к модели и возврат промежуточных данных в её контекст.
Ошибочные попытки с budget включены. Независимое время модели и server load
не контролируется, повторов для устойчивой оценки latency нет.

## Кодовые Исправления

`tools/mcp/discovery.rs` теперь сохраняет предоставленный MCP `outputSchema`
как `ToolSurface::Function.output_schema`, включая nullable/optional поля.
Отсутствие/null остаётся `None`, `{}` сохраняется как явная schema. Никакого
вывода схемы из образца или готового ответа задачи нет. Существующий OpenAI
adapter уже передавал это поле; его mapping не менялся. Назначение поля
соответствует [официальной документации OpenAI](https://developers.openai.com/api/docs/guides/tools-programmatic-tool-calling#configure-programmatic-tool-calling).
Первоначальный fixture сам не объявлял `outputSchema`: потеря discovery —
самостоятельно найденный дефект, а не доказанная причина тех неуспехов.
Core не валидирует `structuredContent` по output schema и не знает предметных
постусловий: наличие схемы помогает писать алгоритм, но не доказывает его.

В `cli_app.rs` stdout теперь дочитывается ограниченным буфером одновременно
с ожиданием exit под прежним общим deadline 2 с. Ранее после shutdown ACK
клиент прекращал чтение, а server мог ещё писать большой финальный snapshot.
На настоящем установленном server без model/tool calls воспроизведено:
после ACK оставалось 109 602 bytes; без drain процесс не выходил, после
возобновления чтения вышел за 8 мс. Это доказанный дефект, хотя причина каждого
исторического timeout отдельно не трассировалась. Ошибка shutdown response
теперь не маскируется timeout cleanup. Полученный ответ one-shot CLI печатает
до shutdown; ошибка завершения сохраняет ненулевой exit.

## Финальная Сборка Со Схемами API

После instruction-only контроля отдельно включили declared API output schemas
и типизированные поля входного отчёта (`--api-schemas`). Они содержат поля и
типы контракта, но не ожидаемые IDs, counts совпадений или суммы. Это отдельная
интеграционная фаза, её результат не приписывается только изменению инструкции.
В canonical requests присутствуют output schemas всех четырёх MCP tools;
реальный provider принял запросы, hybrid/direct обхода CodeMode нет.

Core `af060865be4751e2e8479511db8b276ca546c85d`, Modules
`3193acb35621a16cc04c5a9a9dcac0aff7150ca6` установлены в portable.

`167b4de1a8978e3cbb9cc983b9c8739be1253dcab740f0a6c4782246ecbd4fb2`.

воспроизведение записанного workflow, а semantic correctness — независимый scorer.
