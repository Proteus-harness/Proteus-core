# Ожидаемый Результат

Уточнено с владельцем 2026-10-02.

Proteus — конструктор агентных систем для разных предметных областей.
Первый рабочий пример — близкая реконструкция обычного сценария Codex.
Критерии этой сборки и критерии самого конструктора разделены ниже.

## Результат Для Конструктора

1. Рабочая сборка пригодна для согласованных повседневных задач.
2. Отдельную часть сборки можно полезно заменить через module и config;
   виден небольшой радиус изменений и сохраняется корректность границ.
3. Собственные алгоритмы и сочетания не требуют соответствия Codex.
4. Сборка и проверки воспроизводятся локально, ограничения перечислены явно.
5. Общие границы исполнения не требуют чата или модели, если вызываемая
   операция может работать без них. Сохраняется возможность развивать
   контракты под конкретные задачи. Уже работающий задел и ограничения — в
   [execution-runtime.md](../architecture/execution-runtime.md).

## Критерии Сборки Codex

В выбранном обычном сценарии пользователь не замечает существенной разницы
с Codex. Сравнение на задачах подтверждает совпадение результатов и расхода.

Полное воспроизведение всех мелких фич Codex не требуется.
Текущий статус и уже известные ограничения находятся в [scope.md](scope.md).

## Что Значит Подтвердить Совпадение

На одинаковых записанных model/tool outcomes сравниваются requests,
действия, изменения history и terminal result. Нормализуется только явно
описанная недетерминированность, например ids и timestamps.

На живых задачах фиксируются версии обоих runtimes, модель и её настройки,
provider, исходный репозиторий, tools/permissions и условия cache.
Повторения позволяют отделить различие runtimes от вариативности самой
модели. Учитываются неудачные попытки и весь расход, включая внутренние
model calls, retries и peers, если они входят в сценарий.

Цель — совпадение результатов и расхода. Численный допуск для live измерений
этим документом не назначается. Его нужно определить до оценки вместе
с корпусом задач и количеством повторений. Денежные суммы опираются на
provider cost или одну зафиксированную таблицу цен.

## Граница Следующего Решения

Для сравнения сборки Codex ещё нужно определить обычный сценарий и исключения, pinned
версию Codex, интерфейс оценки и правила измерения. Эти детали пока
не являются согласованным перечнем feature work.

Доведение обычного цикла Codex на Proteus проверяется через конкретные
расхождения с эталоном. Текущая работа над каркасом продолжается через
существующие слоты с сохранением независимой от чата границы исполнения.
Переход к более общему устройству сборок и универсальная регистрация
контрактов отложены до конкретной потребности и отдельного решения владельца.
При переходе выбирается предметный сценарий, который проверяет недостающие
вход, состояние и завершение; пример — в
[execution-runtime.md](../architecture/execution-runtime.md).

Описанные ограничения сами по себе не являются задачами универсализации.
Основание для пересмотра — конкретный сценарий, который не выражается
действующими контрактами с нужной семантикой, либо прямой запрос владельца.

Живое сравнение задач и расхода оставлено на последующий этап; оно остаётся
критерием проверки сборки Codex, но не блокирует текущую работу над каркасом.

Работы по переходу межагентного обмена на A2A отложены владельцем. Они не
входят в текущий этап и возобновляются только по отдельному решению.
Действующим backend AgentControl остаётся local stdio.

Снижение расхода памяти server `proteus` отложено владельцем до отдельного
захода. Известные причины: glibc arenas удерживают освобождённую после хода
память, а запись `before_context` hook invocation в журнале повторяет полную
history примерно восемь раз.

Ориентир для приложения — Codex App по выбранным владельцем экранам: спокойная
тёмная сиренево-серая палитра, компактная навигация, свободная лента чата,
единые скругления, боковая полоса и боковая панель сессий и файлов.
Переходы не должны дёргать содержимое.
Основной клиент — нативное приложение на GPUI. Расширения клиента сохраняют
независимый жизненный цикл. Представление инструментов, настроек и анализа
развивается внутри основного приложения.

Расширения клиента развиваются независимо от модулей агента. Поставляемые
значки и панели, включая квоту подписки, — отдельные процессные пакеты
с тем же публичным контрактом, что и пользовательские расширения. Новые панели подключаются через конкретные договоры
данных.

Доставка процессных модулей через git-каталог отложена владельцем на второй
этап. Нужны отдельное решение о платформенных артефактах и общий путь записи
`components.*` через API; текущий каталог клиента подключает только
расширения клиента, Agent Plugins, навыки и MCP-конфигурации.

Проверки выполняются локально. CI отключён по решению владельца и
не является условием завершения.

Первый явно включаемый режим ограниченного запуска process component под Linux
задаётся через `components.<id>.sandbox`: один export, явные filesystem grants,
сеть закрыта по умолчанию и отказ без unsandboxed fallback. Ответственность
Core/process host, lifetime и оставшиеся границы описаны в
[security-and-policy.md](../guides/security-and-policy.md#ограниченный-запуск-components-под-linux).
Поставляемые profiles сохраняют trusted default. Для stdio MCP server та же
launch policy включается отдельно в `tools.mcp_servers[].sandbox` и действует
на все remote tools одного процесса. LSP, peers и расширения Desktop сохраняют
отдельные launch paths; общая OS-изоляция, quotas и контейнеризация
не объявляются завершёнными и требуют отдельного следующего этапа.
