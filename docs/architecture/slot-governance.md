# Когда добавлять новый слот

Новый слот нужен, когда Core должен вызывать заменяемое поведение, для которого
пока нет контракта. Например, новый алгоритм поиска обычно подключается через
`tool` для явного вызова или `context_provider` для автоматического чтения.
Другие примеры приведены в [таблице ниже](#куда-относится-поведение).

Каталог слотов определяет Core. Объявление export подключает реализацию к известному
слоту. Для нового слота меняются общий контракт, процессный адаптер и конфигурация.
Данные чата и модель входят в контракт только для операций, которым они нужны.

## Условия для нового слота

Сформулируйте, в какой точке Core вызывает новое поведение и какие данные оно
принимает и возвращает. Контракт должен работать с двумя независимыми реализациями
с разными алгоритмами или источниками данных. Проверка замены вызывает обе через
один процессный адаптер с одинаковыми правами. DTO описывают задачу слота и
оставляют детали интерфейса, провайдера и алгоритма внутри реализации.

Для `ordered_many` обе реализации должны быть полезны одновременно. Порядок задаёт
снимок конфигурации. Определите, как разрешаются конфликты, как проверяется
промежуточный результат, что происходит при тайм-ауте или ошибке обработчика и какое
состояние сохраняется при ветвлении, перезагрузке и перезапуске. Проверьте оба порядка
(`A → B` и `B → A`), отмену, сбой одного участника и права каждого.

## Куда относится поведение

| Требуется | Существующее место |
|---|---|
| Хранится или восстанавливается canonical session journal, metadata, blobs и кеши | `session_storage/v2`; порядок lifecycle и принятие ACK принадлежат Core |
| Модель сама вызывает действие | `Tool` |
| Меняется порядок действий агента | `Workflow` |
| Контекст добавляется или сокращается перед вызовом модели | `ContextBuilder`, `context_provider` или `BeforeContext`/`BeforeModel` hook |
| Выбирается, какие инструменты показать модели | `BeforeToolSelection` hook |
| Ищутся данные в проекте | `Tool` для явного действия, `context_provider` для автоматического добавления контекста |
| Долговременная память явно сохраняется или читается | `Tool`; автоматическое чтение — `context_provider`, durable storage принадлежит implementation |
| Принимается решение `allow` / `ask` / `deny` | `ApprovalPolicy` и передача решения на подтверждение |
| Применяется изменение файла | `Tool`, включая process tool `apply_patch`; алгоритм принадлежит implementation |
| Меняется запрос к провайдеру, поток ответа или учёт использования | `Model` и его контракт обмена с процессом |
| Показывается отладочная информация или меняется интерфейс | протокол сервера приложения или клиент UI/CLI |
| Несколько независимых обработчиков последовательно меняют один DTO | Возможный контракт `ordered_many`; сначала нужны два одновременных применения и правила цепочки |

## Несколько идей в одной сборке

Профиль может сочетать workflow одного проекта, инструмент другого и собственную
политику. В `pack` входят конфигурация, реализации, документация и проверки их
совместной работы. Совместимость с исходным проектом проверяется
для поведения, которое обещает профиль.

## Исследовательский модуль

Пока общий контракт не определён, прототип можно держать в `Proteus-modules/research`
вне рабочего профиля. В README достаточно описать, какого контракта не хватает.
Так устроен `research/tool-output-artifacts`, эксперимент с артефактами вывода инструмента.

## Что требуется перед объединением изменений

Опишите DTO и trait в `proteus-contracts`, поддержите слот в процессном протоколе
и настройке Core. Задайте поведение при отсутствии выбора и приведите рабочий пример
конфигурации. Добавьте слот в [каталог](modules.md#слоты-и-их-выбор) и [таблицу прав](process-module-architecture.md#authority-table).
Проверки протокола и замены реализации перечислены в [матрице изменений](../development/testing.md#evidence-matrix).

## Упорядоченные обработчики `hook/v8`

Например, `modules.hooks` позволяет включить добавление инструкций и ограничение
вывода инструмента в одном профиле. Core вызывает обработчики в порядке конфигурации
и проверяет результат каждого. До вызова инструмента ошибка останавливает цепочку.
После вызова инструмента сохраняются и фактический результат, и ошибка обработчика.
Доступные точки вызова и правила завершения описаны в [контракте hooks](process-module-architecture.md#typed-hook-chain).
